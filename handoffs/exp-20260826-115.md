## Hypothesis

- Target case/shape: all four public 128-aligned shapes, with fixed epilogue work most exposed in the two `K=2048` cases.
- Code region: the two MACA epilogue b64 output-store sites and only the adjacent-lane value ownership required to widen them.
- Mechanism family: width-16 adjacent-lane value-owner remap plus predicated b128 global store.
- Falsifiable hypothesis: moving each odd lane's adjacent b64 payload into its even neighbor and issuing one predicated b128 store from the even owner reduces 4,096 active b64 lane stores to 2,048 active b128 lane stores per CTA and has at least a 1% opportunity without changing output bytes or transactions.
- Expected structural change: the proposed mapping would preserve 32,768 output bytes, 256 aligned 128-byte cache-line covers, 128x128 ownership, arithmetic, MMA/shared work, barriers, grid and ABI. It necessarily adds two 32-bit width-16 shuffles for each of 16 per-lane payload sites: 8,192 lane shuffle invocations, or 128 wave shuffle issues per CTA. The 64 wave store issue positions remain 64 because all four wave64 groups still execute every unrolled row/column store site with odd owners predicated off.

## Proof And Tests

- Address/coverage proof: exhaustive enumeration of all 256 threads, two row groups, four rows and two output-column groups proves the current 4,096 b64 stores cover all 16,384 BF16 coordinates exactly once. Pairing local lanes `(0,1), (2,3), ..., (14,15)` produces exactly 2,048 conceptual b128 stores and the same 16,384-coordinate exact cover with no duplicates or holes. The peer is always `tid+1` from an even local lane, so lane 15/16 never pair across a width-16 group. `mma_output_row_local` is independent of `tid%16`, making each pair's row equal; the odd column is exactly the even column plus four BF16 values. Even columns are multiples of eight BF16 values, and every public row stride and tile-N offset is a multiple of 128 BF16 values, so every conceptual b128 address is 16-byte aligned and in bounds. All public EM/N values are multiples of 128, making the paired row/column tail predicates jointly true exactly where both baseline stores are true.
- Payload proof: each odd b64 contains two independent 32-bit words. An even owner therefore needs at least two 32-bit cross-lane transfers. Synthetic distinct low/high words for every pair reconstruct the only valid b128 word order `[even.low, even.high, odd.low, odd.high]` with zero mismatches. A single 32-bit shuffle cannot transfer the required 64 payload bits, and changing conversion or ownership mapping to avoid this lower bound is outside the lane.
- Transaction/instruction proof: baseline and conceptual candidate each touch exactly 256 aligned 128-byte cache lines per CTA, with no byte or line reduction. At wave64 issue granularity, the unrolled `2 row groups * 4 rows * 2 column groups` gives 16 store sites per wave and four waves, so both versions retain 64 store issue positions. Every lane must converge on two 32-bit shuffles at each site, adding `256 * 16 * 2 = 8,192` lane invocations, equivalently `4 * 16 * 2 = 128` wave shuffle issues. Thus the candidate saves no wave store issue and no memory transaction while strictly adding 128 wave instructions, owner predicates, two received words and a wide value carrier. The baseline already sits at the allowed 254 MT registers, leaving no resource headroom for the added live payload.
- Synchronization proof: a legal implementation would require every participating lane to execute both shuffles convergently before the even-owner store. The model enforces that condition and introduces no barrier, but convergence is precisely why the 8,192 shuffle-invocation lower bound cannot be reduced by branching only even lanes.

## Decision

- Observed result: the feasibility model disproves the required structural opportunity. The proposed remap halves active lane-level store operations only; it leaves wave store issue positions and 128-byte transactions unchanged while adding the irreducible equivalent of 128 wave shuffle issues per CTA. There is no defensible path to a 1% gain within the assigned single mechanism.
- Risks or unresolved OJ-environment behavior: a future target instruction that directly gathers an adjacent lane's 64-bit payload into a b128 store could change the lower bound. The documented b128 store alone does not provide that cross-lane gather. Compiling the current design would also risk exceeding the exact 254-MT resource ceiling.
- Historical denylist checked: no plain b64 change, guessed b128 ABI, unmapped b128 store, direct accumulator access, BF16 conversion change, scale shuffle/preload, BSM, K64, direct-A, tile/grid/cluster/specialization change or second mechanism was implemented.
- Recommendation: reject
- Independent audit required: no; no source, thread mapping or intrinsic use was committed. Any future implementation after new hardware evidence would require an independent mapping/convergence audit.
- Suggested next action: close adjacent-lane b128 owner remap. Reopen only with authoritative target evidence for a single instruction that combines cross-lane gather and b128 store, or evidence that the existing contiguous b64 pattern generates more than the modeled 256 cache-line transactions.
